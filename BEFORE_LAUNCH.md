# Before official launch

A punch list of what's genuinely solved vs. what's still missing before this can be handed to
other teams as shared infrastructure, not just a working prototype. See `PROJECT_CONTEXT.md` for
how the project works today; this file is specifically about closing the gap to a trustworthy
org-wide release.

## Already solid (don't re-litigate these)

- Framework-agnostic core (Shadow DOM Web Components) + typed `@brandsync/react` /
  `@brandsync/angular` wrapper packages, published to public npm.
- Real design tokens (`brandsync-tokens`) with light/dark theming, verified per component.
- Documented customization contract — CSS custom properties, shadow parts, slots (see
  `CONVENTIONS.md`) — so teams can extend without forking or breaking encapsulation.
- Figma → code workflow that visually verifies against the real design every time, not just "build
  succeeded."
- Three-layer test coverage (unit, real-browser component tests, Storybook-as-tests) with an
  accessibility addon wired into Storybook.
- Onboarding docs exist: `CLAUDE.md`, `CONVENTIONS.md`, `readme.md`, `PROJECT_CONTEXT.md`.

## Gaps to close before launch

### 1. No CI
There is no `.github/` workflow at all. Tests, builds, and publishing are 100% manual, run from
one person's machine. Nothing currently stops a broken component from being published.
**Needed:** a CI pipeline that runs the full test suite (and ideally a build) on every PR, blocking
merge on failure.

### 2. Single-maintainer publish bottleneck
Publishing depends on one person's local npm auth (a granular access token with 2FA bypass in a
personal `~/.npmrc`). No one else can cut a release today.
**Needed:** either a shared/org npm account with proper 2FA, or an automated publish step in CI
using a scoped, rotating token — not a personal credential.

### 3. Still on 0.0.x versioning
npm's semver rules make `^0.0.x` behave like an exact pin. Every release currently requires
manually bumping the dependency pin in both wrapper packages by hand, or consumers risk two
non-deduped copies of `@brandsync/wc` (duplicate custom-element registrations).
**Needed:** move to `0.1.0`+ before launch, and/or adopt lockstep release tooling (e.g.
Changesets) so this isn't a manual, error-prone step forever.

### 4. Narrow component coverage
15 components today, and roughly half (`bs-composer`, `bs-chatbot-*`, `bs-ai-thinking`) are
purpose-built for one product surface (Genie AI chat), not general-purpose. A typical
CRUD/dashboard team would hit gaps immediately: no select, checkbox, radio, switch, tabs, toast,
breadcrumb, pagination.
**Needed:** either scope the initial launch explicitly as "Genie AI chat components + a handful of
primitives" (honest framing), or prioritize the missing general-purpose primitives first.

### 5. No changelog or versioning policy
Consuming teams have no way to know what changed between versions, or whether a given bump is
safe, beyond reading raw git history.
**Needed:** a `CHANGELOG.md` (can be auto-generated by the same tooling that solves #3) and a
stated policy for what counts as a breaking change.

### 6. Known, unfixed accessibility regression
`bs-modal`'s focus-restoration tests have been failing throughout this project's history and were
never actually fixed — only documented as "pre-existing." This is a real behavior gap (focus may
not correctly return to the trigger element on close), not just test debt, in a component other
teams would rely on for accessible modals.
**Needed:** actually fix this before launch, not just note it.

### 7. No enforced visual regression testing
Screenshot tests exist for exactly one component (`bs-modal`), applied inconsistently, and nothing
enforces them since there's no CI.
**Needed:** either extend screenshot coverage to all components or explicitly decide visual review
happens manually per PR (and say so).

### 8. No contribution / governance process
There's no documented process for other teams to propose new components, request changes, or
learn when a breaking change is coming. Today it's whatever conversation produced the last commit.
**Needed:** even a lightweight `CONTRIBUTING.md` (how to propose a component, who approves,
deprecation policy) before external teams start depending on this.

## Suggested order of attack

1. CI (tests + build gate on PRs) — cheapest, highest-leverage, unblocks everything else.
2. Fix the `bs-modal` focus-restoration bug — a real user-facing a11y issue, not process debt.
3. Versioning/changelog tooling (Changesets or equivalent) + bump to `0.1.0`.
4. Decide and document the "shared publish credential" story.
5. Write `CONTRIBUTING.md`.
6. Only then: prioritize new general-purpose components based on real team demand.
