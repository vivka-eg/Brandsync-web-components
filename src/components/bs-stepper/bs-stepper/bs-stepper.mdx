## Overview

A sequence of named steps showing overall progress through a multi-step flow (e.g. a checkout, an
onboarding wizard) -- each step reads as enabled (not yet reached), current, done, error, or
disabled, connected by a rail between them.

The stepper is built from two composable elements, the same slotted-composition architecture as
Carbon Design System's `cds-progress-indicator`/`cds-progress-step`:

- **`bs-stepper`** -- the container. Renders a plain `<slot>` and propagates
  `currentStep`/`direction`/`showDescription` down to its slotted steps as JS properties -- the
  same "container pushes state onto its slotted children" pattern `bs-tabs` uses for `selected` and
  `bs-breadcrumbs` uses for `size`.
- **`bs-stepper-step`** -- one step: an icon/indicator plus a name and optional description,
  connected to the next step by a trailing rail. Each step computes its own
  `enabled`/`current`/`done` state from its position among its siblings relative to `currentStep`,
  unless its own `error`/`disabled` prop overrides it.

This is a static status display, not an interactive control -- Figma's spec shows no hover/pressed
treatment on any step, so nothing here is clickable.

**When to use**
- Showing where the user is in a fixed, ordered, multi-step flow.

**When not to use**
- A flow whose steps aren't fixed/known in advance -- a stepper implies the full sequence is
  already known.
- As a substitute for actual in-page navigation between steps -- pair this with real controls
  (Next/Back buttons) elsewhere in the flow, this component only displays status.

## Vertical

`direction="vertical"` puts each step's icon beside its name/description in a row, connected by a
vertical rail, instead of the default horizontal layout (icon above name/description, connected by
a horizontal rail).

<Canvas of={StepperStories.Vertical} />

## Error and disabled steps

A `bs-stepper-step`'s own `error`/`disabled` attribute overrides whatever state its position
relative to `currentStep` would otherwise derive -- e.g. a step before `currentStep` would normally
read as "done", but `error` on that step shows the error treatment instead. `disabled` takes
priority over `error` if a step somehow has both set.

## No description

`show-description="false"` on the container hides every step's description, regardless of whether

## Component API

<Controls of={StepperStories.Default} />

### bs-stepper

| Prop | Attribute | Type | Default |
|---|---|---|---|
| `currentStep` | `current-step` | `number` | `0` |
| `direction` | `direction` | `'horizontal' \| 'vertical'` | `'horizontal'` |
| `showDescription` | `show-description` | `boolean` | `true` |

**Customization surface**:
- Slots: default (the `bs-stepper-step` children, in order)
- CSS Custom Properties: `--bs-stepper-edge-padding` -- `direction="horizontal"` only. Every step's
  name/description centers under its own icon, including the first and last steps, whose icons sit
  flush against the container's own edges -- this padding exists to give that centered text
  somewhere to overflow into without clipping against the edge. See `bs-stepper.css`'s header block
  for what it aliases to.

### bs-stepper-step

| Prop | Attribute | Type | Default |
|---|---|---|---|
| `name` | `name` | `string` | `''` |
| `description` | `description` | `string` | `undefined` |
| `error` | `error` | `boolean` | `false` |
| `disabled` | `disabled` | `boolean` | `false` |
| `computedState` | `computed-state` | `'enabled' \| 'current' \| 'done'` | `'enabled'` (normally set automatically by the parent `bs-stepper`) |
| `direction` | `direction` | `'horizontal' \| 'vertical'` | `'horizontal'` (normally set automatically by the parent `bs-stepper`) |
| `showDescription` | `show-description` | `boolean` | `true` (normally set automatically by the parent `bs-stepper`) |

**Customization surface** (see `CONVENTIONS.md` in the repo root for the full convention):
- Shadow parts: `::part(icon)`, `::part(label)`, `::part(name)`, `::part(description)`,
  `::part(connector)`
- CSS Custom Properties: `--bs-stepper-step-gap`, `--bs-stepper-step-icon-size`,
  `--bs-stepper-step-icon-border-width`, `--bs-stepper-step-connector-color`,
  `--bs-stepper-step-connector-thickness`, `--bs-stepper-step-icon-border-enabled`,
  `--bs-stepper-step-icon-border-current`, `--bs-stepper-step-icon-dot-current`,
  `--bs-stepper-step-icon-bg-done`, `--bs-stepper-step-icon-color-done`,
  `--bs-stepper-step-icon-border-error`, `--bs-stepper-step-icon-color-error`,
  `--bs-stepper-step-icon-border-disabled`, `--bs-stepper-step-text-enabled`,
  `--bs-stepper-step-text-active`, `--bs-stepper-step-text-disabled`,
  `--bs-stepper-step-font-size`, `--bs-stepper-step-line-height`,
  `--bs-stepper-step-name-font-weight`, `--bs-stepper-step-description-font-weight` -- see
  `bs-stepper-step.css`'s header block for what each aliases to.

## Accessibility

- Each `bs-stepper-step` sets `role="listitem"` on its own host, since it's a custom-element child
  rather than a real `<li>` -- mirroring the same reasoning `bs-breadcrumb`/`bs-breadcrumb-overflow`
  already use for the identical situation.
- Each step's icon is purely decorative (the checkmark/dot/exclamation carry no information beyond
  what the step's own state class already conveys) -- consider pairing a stepper with an
  `aria-live` region elsewhere in your flow that announces step changes, since this component
  itself doesn't (it's a static display, re-rendered whenever `currentStep` changes, with no
  built-in announcement).
- Every rail segment (`part="connector"`) is `aria-hidden` -- purely a visual guide between steps.
- Name/description are plain text content, not interactive -- there's nothing to focus or activate
  here by design (see the Overview's note on this being intentionally non-interactive).
